# 求职准备推进方案——八股与项目经验

## 一、核心策略

求职准备不能在“背八股”和“做项目”之间二选一，应采用双线推进：

> **八股保证进入技术面，项目决定面试深度和个人区分度。**

建议根据求职阶段动态调整时间：

| 阶段 | 八股 | 项目 |
|---|---:|---:|
| 当前实习积累期 | 40% | 60% |
| 集中投递前一个月 | 60% | 40% |
| 面试密集期 | 70% | 30% |

个人项目方向具有一定优势，当前更需要补齐三项短板：

1. Java 后端基础知识缺少系统化组织；
2. 项目代码、测试、指标和 Git 证据不足；
3. AI 参与较多，但个人决策、验证和维护能力尚需明确证明。

## 二、八股学习顺序

### 第一层：Java 核心

优先掌握：

- ArrayList、LinkedList、HashMap、ConcurrentHashMap；
- 面向对象、泛型、反射和注解；
- 异常体系；
- IO 与 NIO；
- Java 内存模型；
- volatile、synchronized、CAS；
- 线程池、ThreadLocal 和各类锁；
- CompletableFuture；
- JVM 内存结构；
- 类加载机制；
- GC 算法和垃圾收集器；
- JVM 问题排查基础。

每个主题必须能够回答：

1. 它是什么；
2. 为什么这样设计；
3. 使用时有什么风险；
4. 在项目中哪里可能用到；
5. 出现问题时如何排查。

### 第二层：Java 后端必备

- Spring IOC、AOP；
- Bean 生命周期；
- Spring 事务及失效场景；
- Spring MVC 执行流程；
- Spring Boot 自动配置；
- MyBatis 执行流程和缓存；
- MySQL 索引、B+树、事务、MVCC 和锁；
- Redis 数据结构、缓存问题和分布式锁；
- 消息队列基本模型；
- HTTP、HTTPS 和 TCP；
- Cookie、Session 和 JWT；
- Linux 常用排查命令；
- Git 分支与团队协作流程。

### 第三层：项目强相关专题

结合飞冰运营自动化重点学习：

- 接口幂等；
- 异步任务状态机；
- 超时、有限重试和退避；
- 限流与并发控制；
- 数据一致性；
- 事务、补偿和回滚；
- 任务队列；
- 乐观锁、悲观锁和数据库锁竞争；
- 日志、审计和可观测性；
- 权限与人工审批；
- 敏感信息和密钥管理。

### 第四层：AI 应用知识

- 大模型 API 调用；
- Prompt 与上下文窗口；
- 结构化输出和 JSON Schema；
- Tool Calling；
- Embedding 和向量检索；
- RAG 基本流程；
- Agent 与确定性工作流的区别；
- 模型幻觉和 Prompt 注入；
- 模型评测；
- Token 成本、延迟和调用监控；
- 权限、审批和审计；
- 模型理解与确定性执行的边界。

AI 应用知识用于形成差异化，但不能替代 Java 基础。

## 三、八股学习闭环

八股学习分为两个层次：学习闭环用于规定“怎么学”，单题模板用于规定“每道题需要掌握和表达什么”。

### 1. 理解

先弄懂设计动机和运行原理，不急于背标准答案。

### 2. 压缩

每道题准备三种回答：

- 30 秒结论；
- 2 分钟完整回答；
- 可继续深挖的原理、源码、场景和边界。

### 3. 主动回忆

合上资料后直接口述或手写，再检查遗漏。建议每天复习：

- 当天新学问题；
- 前一天问题；
- 三天前问题；
- 一周前问题。

### 4. 绑定项目

| 八股知识 | 飞冰或个人项目场景 |
|---|---|
| 数据库锁 | 欢迎语批量修改出现锁等待 |
| 并发控制 | 并发数由 5 降至 2 |
| 重试机制 | 网络超时和临时锁竞争 |
| 接口幂等 | Agent 重复提交运营任务 |
| 异步任务 | 客服修改接口受理后延迟生效 |
| 回滚 | 链接和客服修改前保存原始配置 |
| 人工审批 | License 激活属于不可逆操作 |
| 本地持久化 | DailyFlow 使用 SQLite |
| IPC | Electron 主进程与渲染进程通信 |
| 密钥安全 | Token 和 API Key 不进入日志 |

项目场景能够帮助理解八股，八股原理也应反过来改进项目设计。

### 5. 单题标准模板

每道八股题统一整理为一张问题卡。模板用于保证理解和表达完整，不要求机械填满所有栏目；与题目无关的部分可以省略。

#### 题目

写成面试官可能直接提出的问题，避免只记录“HashMap”“Spring 事务”之类宽泛主题。

#### 30 秒结论

用 3—5 句话直接回答问题，包含核心结论、关键原因、重要边界和一句项目关联。该部分应能够脱离笔记直接口述。

#### 一、它是什么

- 解决什么问题；
- 核心概念和组成是什么；
- 在技术体系中处于什么位置；
- 输入、处理过程和结果分别是什么。

#### 二、为什么这样设计

- 原来需要解决什么问题；
- 当前方案的核心设计动机；
- 为什么不采用其他方案；
- 获得了什么优势；
- 付出了什么代价。

#### 三、它是怎么运行的

按照执行顺序说明入口、关键步骤、涉及的数据结构或组件、最终结果以及异常分支。必要时使用流程图、时序图、伪代码或关键源码辅助理解，不大段照抄源码。

#### 四、风险与适用边界

根据题目实际情况，从以下方面选择需要回答的内容：

- 并发安全；
- 数据一致性；
- 性能和内存；
- 异常与失败；
- 配置或使用错误；
- 安全风险；
- 不适用场景。

#### 五、项目绑定

使用“场景—问题—方案—结果—反思”结构：

- **场景**：当时在做什么；
- **问题**：遇到了什么现象或风险；
- **方案**：如何利用该知识分析或解决问题；
- **结果**：取得了什么可验证结果；
- **反思**：重新设计时会如何改进。

如果项目中没有实际使用，应明确区分“真实经历”和“可能应用”，不得为了面试编造项目经验。

#### 六、出现问题时如何排查

1. 观察现象、影响范围和触发条件；
2. 查看日志、指标和运行状态；
3. 使用命令或工具缩小问题范围；
4. 提出假设并设计验证方法；
5. 确认根因；
6. 制定临时止损方案；
7. 完成长效修复、测试和复盘。

#### 七、对比与选型

- 与相似方案有什么区别；
- 各自适合什么场景；
- 项目为什么选择当前方案；
- 什么情况下不应该使用；
- 如果重新设计，是否仍会选择它。

#### 八、高频追问

每道题准备 3—5 个后续问题，覆盖原理、源码、项目场景、异常情况和适用边界。这里只记录答题关键词，避免问题卡无限膨胀。

#### 九、2 分钟完整回答

按照“结论 → 设计动机 → 核心原理 → 风险边界 → 项目场景”的顺序，整理为一段自然、连贯、可直接口述的回答。

#### 十、掌握与复习记录

```text
掌握程度：陌生 / 理解 / 能口述 / 能追问 / 能结合项目
首次学习：
最近复习：
下次复习：
口述卡点：
遗漏内容：
```

建议在当天、第 1 天、第 3 天、第 7 天、第 14 天和第 30 天进行主动回忆；已经稳定掌握的问题可以适当延长复习间隔。

## 四、简历项目选择

简历优先保留两项核心项目，避免堆砌大量浅层经历。

### 主项目：飞冰运营 Agent / 业务 Skill 执行平台

项目目标：把门店链接、客服绑定、账户激活、欢迎语配置等高频运营能力封装为 Agent 可安全调用的 Skill。

应逐步建设：

- 自然语言或结构化需求输入；
- Excel 数据解析和校验；
- Skill 注册、发现与选择；
- 输入输出 Schema；
- dry-run；
- 风险分级；
- 人工审批；
- 异步任务；
- 幂等；
- 超时和重试；
- 结果验证；
- 日志审计；
- 回滚、补偿或人工兜底。

项目表述必须区分：

- **已完成**：茶瀑布真实脚本、批量执行、日志、备份、回滚和业务结果；
- **正在建设**：统一 Skill 规范和执行框架；
- **后续计划**：自然语言入口、模型路由和多 Skill 编排。

不得把设想包装成已完成成果。

### 辅助项目：DailyFlow 桌面任务与总结助手

可用于证明 0→1 产品和全栈能力：

- Electron；
- Vue 3、TypeScript 和 Pinia；
- SQLite 本地持久化；
- 主进程、渲染进程、Preload 和 IPC；
- AI 总结与结果预览；
- 系统凭据存储；
- Vitest；
- Windows 安装包和便携版构建。

需要补齐：

- 规范 Git 仓库；
- 连续且有意义的提交；
- README 和架构图；
- 可运行安装包；
- 功能演示视频；
- 测试结果；
- Bug 的复现、根因、修复和回归记录；
- 个人独立负责的模块说明。

会议转写工具可以放入“其他项目或个人工具”，不占据核心项目位置。

- Skill 执行流程；

- 异常处理矩阵；

### 5. 明确个人与 AI 的贡献边界

需要能够说明：

- 业务关系由谁梳理；
- AI 生成了哪些内容；
- 如何审查和验证生成代码；
- 发现并修复了什么问题；
- 哪些设计决策由个人作出；
- 离开 AI 后能否读懂、调试和维护项目。

## 六、简历项目描述草稿

### 飞冰运营业务自动化与 Skill 化实践

面向门店链接、客服绑定、账户激活和欢迎语配置等高频运营需求，在原有 Node.js 脚本库基础上建设批量执行方案，并探索将稳定业务能力封装为 Agent 可调用的 Skill。

- 梳理三方 ID、店铺 ID、企微 userID 及桌台配置之间的数据关系，完成 53 家门店的链接、客服和账户处理；
- 为批量写入增加 dry-run、输入校验、写前备份、执行日志和回滚机制，降低错误配置影响；
- 针对异步接口“受理成功但未立即生效”的问题，增加延迟查询和结果抽查流程；
- 定位欢迎语字段反向语义和数据库锁竞争问题，通过请求体差异分析、降低并发、延长超时及退避重试处理 1007 个桌台，其中 1004 个成功，剩余异常明确记录并转人工；
- 编写上手文档和异常处理方案，使 Agent 或操作人员能够依据文档完成执行、验证和兜底。

统一 Skill 平台完成后，再将相应架构和 Java 后端成果加入简历。

## 七、项目面试六层准备法

### 第一层：两分钟项目介绍

讲清背景、问题、个人职责、核心方案和最终结果。

### 第二层：技术架构

讲清技术选型、系统分层、数据流和模块协作。

### 第三层：真实难点

至少准备三个实际问题：

- 异步接口受理成功但未生效；
- 数据库锁等待；
- 不可逆激活操作；
- 多种业务 ID 映射；
- 批量操作部分失败。

### 第四层：方案取舍

能够回答：

- 为什么不用整表覆盖；
- 为什么降低并发；
- 为什么不用直接改数据库；
- 为什么需要 dry-run；
- 为什么高风险任务需要人工审批；
- 为什么平台使用 Java、执行层可以保留 Node.js 脚本。

### 第五层：异常与扩展

能够回答：

- 执行到一半服务宕机怎么办；
- 用户重复提交怎么办；
- 多个 Agent 同时修改同一门店怎么办；
- Token 过期怎么办；
- 如何避免重试重复消耗 License；
- 如何扩展到多个商户并隔离数据。

### 第六层：项目复盘

能够说明当前缺陷、重新设计方案、脚本与正式后端的边界、Agent 可能出错的位置，以及如何评价系统可靠性。

## 八、日常执行节奏

### 工作日参考安排

- 45 分钟：学习一个 Java、数据库或中间件专题；
- 20 分钟：闭卷口述历史问题；
- 实习时间：争取真实模块和 Skill 场景；
- 30 分钟：记录当天技术问题、个人决策和项目证据；
- 20 分钟：把一个真实问题关联到八股知识。

### 周末参考安排

- 2 小时：系统复习本周八股；
- 2 小时：完善核心项目；
- 1 小时：整理 Git、README、测试和指标；
- 1 小时：模拟项目面试并录音复盘。

时间不足时，至少保证：

1. 每天进行主动回忆；
2. 每周有项目代码、测试或可验证文档产出；
3. 每周完成一次项目口述；
4. 每项成果都有证据链。

## 九、三个月推进计划

### 第一个月：基础第一轮与项目规范化

- 完成 Java 集合、并发、JVM、Spring 和 MySQL 第一轮；
- 建立八股问题库和间隔复习机制；
- 将茶瀑布自动化整理为有 Git 记录的项目资产；
- 补齐 README、测试、架构和异常记录；
- 为 DailyFlow 建立规范仓库和演示材料。

验收结果：可以系统回答 Java 核心问题，并完整讲解茶瀑布需求的背景、方案、难点和结果。

### 第二个月：平台实现与模拟面试

- 完成 Redis、消息队列、网络、Linux 和系统设计基础；
- 使用 Java 实现运营任务、审批或 Skill 执行框架；
- 接入第一个真实业务 Skill；
- 每周至少进行一次模拟面试；
- 形成第一版正式简历。

验收结果：既能讲单个自动化脚本，也能解释脚本如何演进为可靠的后端任务和 Skill 平台。

### 第三个月：第二轮复习与求职验证

- 进行八股第二轮和高频错题复习；
- 完成 2—3 个业务 Skill 接入；
- 补齐幂等、任务状态、审计、测试和结果验证；
- 建立两个核心项目的六层追问题库；
- 开始投递，并根据真实面试反馈修正。

验收结果：高频 Java 八股能够自然表达，两个核心项目能够承受连续追问，并有代码、提交、测试和业务结果作为证据。

## 十、统一推进闭环

```text
真实项目遇到问题
→ 查清底层原理
→ 形成八股理解
→ 改进项目设计
→ 留下代码、测试和指标
→ 转化为简历描述
→ 准备面试追问
→ 根据面试反馈继续修正
```

最终需要达到：

- 高频 Java 八股能够自然表达；
- 重要原理能够关联真实项目；
