# AI 应用后端与业务自动化发展规划

## 一、规划结论

结合当前 Java 后端基础、飞冰科技实习经历及公司的后续方向，现阶段最适合的主攻路线是：

> **以 Java 后端为技术底座，向 AI 应用后端、Agent/Skill 平台和企业业务自动化方向发展。**

目标不是转为纯前端，也不是直接竞争大模型算法岗位，而是成长为能够理解真实业务、改造后端接口、封装业务 Skill、组织 Agent 执行，并通过证据验证结果的复合型工程师。

推荐的岗位优先级：

1. AI 应用后端工程师；
2. AI 自动化工程师；
3. Agent / Skill 平台工程师；
4. Java 后端工程师（AI 应用或企业 SaaS 方向）；
5. 偏开发的技术解决方案工程师。

求职阶段可采用更稳妥的定位：

> **Java 后端基础 + AI 应用开发 + 业务自动化交付。**

## 二、公司方向与个人机会

公司后续存在两条相互关联的路线：

### 1. 借助 AI 重写飞冰现有系统

新系统可以继续沿用原系统已经验证过的产品原型和业务模型，但应逐步解决旧系统中的结构性问题：

- 接口和业务逻辑分散；
- 批量操作依赖人工或临时脚本；
- 权限、审计和回滚能力不完整；
- 接口成功不等于业务结果成功；
- 系统接口主要面向页面，缺少 Agent 友好的业务契约。

重写后的系统不应只服务页面，还应提供规范、稳定、可审计的业务 API，为后续 Skill 化提供能力底座。

### 2. 将系统运营服务交给 AI

门店创建、企微接口激活、客服更换、欢迎语修改、群链接替换、标签和权限配置等运营服务，可以逐步封装成 Skill。Agent 根据需求文档理解目标、补齐参数、选择 Skill、生成计划，并在授权后完成执行和验证。

两条路线的关系是：

```text
飞冰系统重写
→ 形成规范、稳定的业务 API
→ 将 API、业务规则和执行流程封装为 Skill
→ Agent 理解需求并编排 Skill
→ 完成可验证、可追踪、可回滚的运营服务
```

这正是个人最值得深入的位置：同时理解旧业务、参与新系统建设，并把真实运营流程转化为 AI 可安全调用的能力。

## 三、当前能力画像

### 1. 已有较强证据的能力

- 能从客户表达中识别真实业务对象、数据关系和执行约束；
- 能使用 Node.js/JavaScript 编写批量业务脚本；
- 能处理 Excel、第三方 ID、店铺 ID、手机号和企微 userID 等数据映射；
- 能调用现有接口解决门店链接、客服、激活和欢迎语问题；
- 已实践 dry-run、写前备份、执行日志、失败重试、结果抽查和回滚；
- 能将一次性问题转化为脚本、说明文档和可复用操作流程；
- 能使用 Python 建设会议录音转写工具；
- 能跨 Java、Node.js、Python、Vue、Electron 等技术栈解决实际问题；
- 对 Agent、Skill、MCP、知识库和 AI 工作流具有主动研究意识。

### 2. 已接触但证据仍需补强的能力

- Java/Spring Boot 在真实业务系统中的独立开发能力；
- MySQL、Redis、消息队列、事务、并发和权限体系；
- 飞冰正式代码的调试、功能修改和回归验证；
- DailyFlow 中独立完成的代码范围和 Bug 修复过程；
- 自动测试、集成测试、部署和线上观测；
- Git 分支、提交、代码评审和可追溯交付；
- LLM Tool Calling、RAG、评测、状态管理和模型网关。

### 3. 目前主要处于设想阶段的内容

- 完整的 Agent 平台；
- Skill 注册、路由和组合编排；
- 项目级 AI 统一认知层；
- AI 自动验收和独立评估体系；
- 多 Agent 权限和治理平台。

这些设想方向正确，但下一阶段应减少继续扩展概念，优先完成真实业务闭环。

## 四、为什么适合 AI 应用后端方向

在茶瀑布需求中，实际工作已经超出了普通脚本编写：

- 客户提供三方 ID，需要先映射飞冰店铺 ID；
- 客服手机号需要转换为企业微信 userID；
- 客服实际绑定在门店下的桌台或渠道对象上；
- 部分接口异步执行，返回成功不代表立即生效；
- 激活操作会消耗 License，属于不可逆操作；
- 欢迎语字段语义与直觉相反，需要通过请求体差异定位；
- 高并发写入会引发数据库锁竞争，需要控制并发、超时和重试。

这些问题要求开发者同时理解业务、数据、接口、风险和验收。个人已经表现出“根据业务问题选择技术工具，并把处理流程工程化”的倾向，这比单纯掌握某一种语言更适合 AI 应用和企业自动化方向。

## 五、实习期间的五项重点

### 1. 深入掌握飞冰业务对象

需要系统梳理：

- 客户、商户、品牌与门店；
- 员工、企微成员与客服；
- 门店、桌台、渠道码与客户群；
- 应用、授权、接口和 License；
- 欢迎语、企微群链接、标签与渠道；
- 配置数据、运行状态和异步任务；
- 可逆操作、不可逆操作及审批边界。

验收目标：接到一个运营需求后，能够画出涉及的对象、数据、接口、风险和结果验证链路。

### 2. 把 Java 后端练成 AI 执行底座

重点补强：

- Spring Boot 接口和分层设计；
- 统一输入输出与参数校验；
- 身份认证和权限控制；
- MySQL、Redis 和消息队列；
- 事务、并发和接口幂等；
- 异步任务和任务状态机；
- 操作日志与审计；
- 超时、重试、补偿和回滚；
- 单元测试、集成测试和 Docker 部署；
- 指标监控、异常告警和问题追踪。

在系统重写过程中，优先争取运营任务中心、批量操作中心、Skill 执行中心、审批中心或审计中心等完整模块。

### 3. 研究 Skill 工程规范

Skill 不应只是提示词或 Markdown 文档，而应是带有业务契约、执行逻辑、权限规则和验收方式的版本化能力单元。

建议的最小结构：

```text
skills/
└─ replace-store-contact/
   ├─ skill.yaml
   ├─ description.md
   ├─ input.schema.json
   ├─ output.schema.json
   ├─ workflow.yaml
   ├─ policy.yaml
   ├─ executor/
   ├─ validators/
   ├─ rollback/
   ├─ tests/
   └─ examples/
```

每个 Skill 至少需要定义：业务目的、触发条件、禁止条件、输入输出、权限风险、执行步骤、成功证据、失败处理、回滚方式、负责人和版本。

### 4. 掌握模型调用和 Agent 编排

重点学习：

- Prompt 基础和结构化输出；
- JSON Schema；
- Tool Calling；
- 多轮任务状态；
- 上下文管理；
- 模型选择、超时、重试和降级；
- Token 成本与调用监控；
- Prompt 注入防护；
- 模型输出验证和自动评测。

需要坚持的边界：

> **模型负责理解、规划和选择；确定性代码负责校验和执行。**

模型不能自行扩大影响范围、关闭 dry-run、绕过审批、消耗 License 或覆盖原数据。

### 5. 建立证据和验收体系

需要组合三类验收：

- **确定性验收**：参数格式、数据数量、ID 映射、接口状态、前后值对比、幂等键和测试断言；
- **业务验收**：目标门店是否完整覆盖、客服是否实际绑定、欢迎语是否实际发送、License 是否正确消耗；
- **人工验收**：高风险批量操作、不可逆操作、客户内容触达和异常结果。

接口返回 200、脚本退出码为 0 或模型声称成功，都不能单独作为任务完成依据。

## 六、推荐的首个 Skill 化试点

建议从“门店客服批量替换 Skill”开始，因为已有茶瀑布真实案例，且链路足够完整：

```text
运营人员提交需求
→ Agent 识别批量更换客服意图
→ 读取并校验 Excel
→ 映射三方ID、店铺ID、手机号和userID
→ 输出影响范围与异常数据
→ 执行 dry-run
→ 人工确认
→ 创建异步任务
→ Skill 调用业务接口
→ 延迟查询实际结果
→ 对比变更前后数据
→ 输出成功、失败和待人工处理清单
→ 必要时回滚
→ 自动生成执行报告
```

首个试点的验收标准：

- 能识别缺失或异常输入；
- 能准确计算影响范围；
- 默认只进行预演；
- 正式执行必须经过授权；
- 重复执行不会造成重复副作用；
- 能查询真实业务结果；
- 失败项可以重试、回滚或转人工；
- 自动生成可审计的执行报告。

第一个 Skill 稳定后，再接入入群链接替换、欢迎语修改和账户激活。多个 Skill 出现相同需求后，再抽取统一平台能力。

## 七、建议的系统分层

### Agent 层

负责自然语言理解、需求澄清、任务规划、Skill 选择和用户交互。

### Skill 层

负责业务能力定义、输入输出契约、适用条件、风险等级、工作流、验收标准和失败策略。

### 执行层

负责调用 Java Service、Node.js/Python 工具、任务队列、幂等、超时、重试、补偿和回滚。

### 治理层

负责身份、最小权限、人工审批、密钥管理、操作审计、成本限制、敏感信息处理和风险拦截。

模型配置建议统一放入模型网关，避免模型名称、供应商、超时和密钥散落在各个 Skill 中。

## 八、三个月实践路线

### 第一个月：业务理解与单 Skill 闭环

- 梳理飞冰核心业务对象关系；
- 阅读旧系统对应代码和接口；
- 选择客服或链接场景；
- 定义 Skill 输入、输出、权限、风险和验收；
- 实现 dry-run；
- 实现真实调用、执行记录和人工确认；
- 使用脱敏数据完成端到端试跑。

阶段成果：一个能够从需求进入、经过审批、完成执行并输出验证报告的真实 Skill。

### 第二个月：接入多个 Skill 并抽取公共能力

- 接入第二、第三个业务 Skill；
- 形成统一 Skill 描述格式；
- 建立 Skill 注册和发现；
- 建立任务状态机；
- 实现统一日志、审批、重试和回滚；
- 增加正常、异常和边界测试；
- 记录不同模型的需求解析准确率。

阶段成果：一套可以接入多个飞冰运营能力的最小执行平台。

### 第三个月：可靠性与新系统集成

- 对接重写后的飞冰接口；
- 增加用户身份和权限；
- 增加幂等、审计和告警；
- 建立脱敏异常案例集；
- 建立 Agent 评测；
- 对比人工、AI 辅助、AI 自动三种模式；
- 统计成功率、耗时、成本和人工接管率。

阶段成果：有真实业务指标和执行证据的飞冰运营 Agent 原型。

## 九、时间分配建议

- 40%：飞冰业务和旧系统代码；
- 30%：Java 后端及新系统工程能力；
- 20%：Agent、Tool Calling、Skill 和评测；
- 10%：Node.js、Python、Vue 等辅助技术。

业务和后端工程是根基，AI 是能力放大器。避免把大部分时间用于追逐不断变化的 Agent 框架，最后只形成无法承担真实运营任务的演示。

## 十、需要避免的误区

1. **先造通用平台，后寻找场景**：应从一个真实业务闭环出发，再抽取平台结构。
2. **只研究架构，不实际运行**：下一阶段最缺的是执行证据，而不是更多架构图。
3. **把调用成功等同于业务成功**：必须查询并验证真实结果。
4. **过早追求无人监管**：先采用“AI 计划—人确认—AI 执行—系统验证—异常转人工”。
5. **为了重写而重写**：新系统应解决旧系统的问题，并为 Agent 提供可靠接口。
6. **依赖模型完成确定性判断**：权限、范围、幂等、审批和数据校验必须由代码约束。
7. **忽略 Git 和证据链**：每个成果都应保留需求、设计、分支、提交、测试、执行记录和复盘。

## 十一、实习结束时的目标成果

建议以以下结果作为阶段验收：

- 3 个经过脱敏或真实场景验证的业务 Skill；
- 1 套统一的 Skill 描述和版本规范；
- 1 个任务执行、审批、日志和验收的最小框架；
- 1 套异常案例与自动测试；
- 1 份人工、AI 辅助和 AI 自动执行对比报告；
- 完整的 Git 提交、架构说明和演示材料；
- 能独立讲清一个需求从自然语言到真实业务结果的全链路。

## 十二、最终能够实现什么

这条路线最终不是简单实现“让 AI 帮程序员多写代码”，而是让飞冰的运营人员只需要描述目标，系统即可理解需求、核对数据、生成计划，在获得授权后调用业务能力完成操作，并交付可验证、可追踪、可回滚的结果。

个人最终应成长为团队中能够贯通以下环节的人：

> **理解飞冰业务 → 参与系统重写 → 设计 Agent 友好接口 → 封装业务 Skill → 组织安全执行 → 建立可信验收。**

这一能力组合既能服务飞冰的 AI 化目标，也能沉淀为面向 AI 应用后端、Agent 平台和企业业务自动化岗位的核心竞争力。
