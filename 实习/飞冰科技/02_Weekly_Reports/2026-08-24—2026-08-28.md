# 实习周报（2026-08-24—2026-08-28）

## 一、本周工作概述

本周工作主要围绕四条主线展开：一是熟悉飞冰系统的安装、门店、桌台码、企微接口、欢迎语、标签、权限等业务操作；二是进入真实代码与开发环境，完成阿里云代码库接入、Node.js 环境配置及 `web-wxwork-connect` 本地启动；三是建设可持续复用的 AI 工作体系，将规则、知识、脚本和复盘逐步沉淀为 Agent 可以理解并执行的资产；四是建设 Vibecoding 标准开发流程，将 AI 辅助开发从临时对话升级为有阶段、有交付物、有验收门禁的工程化协作方式。

本周最重要的进展，不是单次完成了多少操作，而是初步打通了“统一规则与上下文 → AI 理解业务 → 脚本化执行 → 结果验证 → 文档沉淀”的工作链路。

## 二、本周重点成果

### 1. 建设本机 Agent 权威源与统一协作体系

本周完成了本机 Agent 组织架构的一轮重要演进，以 `D:\AgentRules\AGENTS.md` 作为全机 Agent 的唯一权威规则源，并通过接入手册、软链接和复盘机制，减少不同 Agent 之间规则分散、版本不一致和经验无法复用的问题。

本轮主要完成：

- 明确“权威规则、全局知识库、复盘机制、任务组织规范”四部分协作体系；
- 将 Agent 接入流程标准化为“阅读接入手册 + 建立权威规则软链接”两步；
- 将共享 Skill 清单从人工维护改为通过 `find-skills` 动态查询，避免文档随 Skill 增删而失真；
- 将“总结必须说明最终能实现什么”写入正式规则，要求 Agent 不只报告技术改动，还要讲清业务价值和结果；
- 建立观察进入 `D:\AgentRules\inbox\`、再由复盘机制升级为正式规则的闭环；
- 完成 OpenCode、DSH、Codex 三端规则接入；Codex 的 `C:\Users\施鸿福\.codex\AGENTS.md` 已建立符号链接并指向 `D:\AgentRules\AGENTS.md`，经链接目标与 SHA-256 哈希核验一致。

这项工作的最终价值是：今后只需维护一份权威规则，已接入的 Agent 即可同步遵守；新 Agent 也能通过标准手册快速理解本机的知识库、任务规范和协作方式，为后续构建“可长期训练、可持续复用”的个人 AI 工作系统打下基础。

### 2. 深入复盘 8 月 27 日会议，明确 AI 工作化方向

8 月 27 日内部分享首先梳理了客户、门店、员工、企微成员、群、小程序、授权及接口之间的业务关系，强调开发、排障和客户支持不能只看单点现象，而要沿完整对象关系链定位问题。

会议后半段提出了本周最重要的方法论：AI 不能只作为问答工具使用，而应逐步成为能够理解业务、复用经验并执行工作的助手或代理。AI 本身不了解公司的业务世界，需要持续向其提供代码、文档、案例、日报和历史问题；人则负责目标、背景、约束、判断标准以及最终结果。

会议形成的工作路径可以概括为：

1. 先让 AI 通过业务文档、代码和案例理解现实业务；
2. 从重复、规则明确的小场景开始验证 AI 执行能力；
3. 每次解决问题后，沉淀背景、步骤、关键判断、验收标准和异常处理；
4. 将稳定方法固化为 SOP、Skill 或可执行文档；
5. 逐步把人从重复操作中释放出来，转向客户沟通、复杂判断、创新和学习。

这次会议也让我进一步明确：个人知识库、Agent 权威源、会议转写、脚本说明和日报复盘并不是相互独立的工具，而是在共同建设 AI 所需的业务上下文和长期记忆。

### 3. 将茶瀑布需求落地为 Agent 可执行的自动化闭环

在茶瀑布链接更换需求中，我结合已有业务操作经验和原脚本库，新增 3 个脚本，并补充使用说明与客户需求解决方案。方案不只说明“运行哪个脚本”，还包含需求映射、前置条件、执行步骤、结果验证和异常兜底，使 Agent 能够依据文档完成操作。

同时，针对茶瀑布未发送欢迎语的问题编写处理脚本，将欢迎语恢复发送，并同步补充说明文档和飞冰使用手册。

这项成果是 27 日会议方法论的一次实际验证：从一个重复、规则明确的业务场景切入，把个人经验转化为“脚本 + 文档 + Agent 执行 + 验证 + 兜底”的完整链路，降低对熟练人员口头指导的依赖，也为后续同类客户需求提供可复制模板。

### 4. 建设 Vibecoding 双轨 AI 开发 SOP

本周将已有的 Vibecoding 开发经验沉淀为一套覆盖两类开发场景的双轨 SOP：`vibecoding-sop` 负责 0→1 绿地项目，`brownfield-iteration` 负责 1→N 存量项目迭代。两者共同遵循“人定方向、AI 干活”的协作原则，但针对不同风险采用不同流程。

`vibecoding-sop` 将从零开发拆分为七个阶段：需求梳理、原型设计、架构设计、API 契约、后端开发与测试、前端接入联调、迭代扩展。开发者承担产品经理和架构师职责，AI 作为全栈团队执行；每个阶段都有固定角色、文档交付物和验收门禁，并通过角色锁定、文档驱动、先契约后编码、原型先行、测试与验收五项约束控制项目失控风险。

`brownfield-iteration` 面向已有代码库，强调“贴合 + 不破坏”，并划分为两种模式：新增功能采用“勘探—增量设计—最小侵入—回归”，修复 Bug 采用“复现定位—最小修复—回归”。其核心是先读懂既有架构与约定，让新代码保持原有风格，并用测试证明没有破坏存量功能。

这套体系最终解决的是 AI 编程中常见的需求漂移、越阶段编码、前后端契约不一致、随意重构和缺少验收等问题。以后面对新项目或已有项目，可以先自动分诊开发类型，再调用对应流程，让 AI 开发过程具备明确交付物、阶段边界和质量检查点，也便于不同 Agent 复用同一套开发方法。

## 四、本周反思

1. 本周已经完成较多文档和工具建设，但部分内容仍停留在“已生成、待实测”阶段。可复用资产必须经过真实或脱敏数据试跑，并留下输入、输出、成功标准和失败案例，才能真正具备交接价值。
2. 批量链接、客服、标签、欢迎语和权限操作影响范围较大，后续仍需坚持变更前备份、映射核对、小范围试跑、执行后抽查及保留回滚入口。
3. 本机 Agent 权威源体系及三端接入已经形成。后续规则变更仍需坚持只修改唯一权威源，并定期检查各端链接目标与内容哈希，避免链接失效或产生本地副本。
4. 日报中部分工作状态和验收证据记录不够完整。后续应减少“学习了、处理了”等模糊表述，补充实际结果、数量范围、验证截图或关联提交。
5. 原始记录中曾出现明文凭据。总结型知识库应坚持最小化记录原则；如凭据仍有效，需要完成轮换并使用安全凭据管理方式保存。
