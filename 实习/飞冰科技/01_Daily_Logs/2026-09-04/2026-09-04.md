## 🐛 踩坑与排查

### 1. 自动化能力库首先要治理安全问题

历史脚本并非复制到 GitHub 就能共享。归位审计发现大量 JWT 硬编码，如果直接提交，即使令牌已过期，也会永久留在 Git 历史中。最终采用“源项目保留、复制时脱敏、业务数据不入库、远程仓库再次扫描”的方式完成治理。

可复用原则：**上传前检查代码、历史、`.env`、input/output 和 records；发现令牌时先脱敏，再建立 Git 历史。**

### 2. “自动提交”必须通过真实业务验证

最初的自动提交只是设计方案，尚不能称为已实现。只有本机 Skill 安装、规则固化并通过渠道欢迎语换图需求完成分支、commit 和 push 后，才形成可验证的闭环。以后区分“规范已写”“Skill 已安装”“业务已跑通”三个状态。

### 3. 批量写入不能把接口成功等同于最终验收

渠道欢迎语 13,071 条提交成功只证明接口接收成功，最终图片是否正确展示仍需后台抽样。批量写操作应坚持：输入核验 → dryRun → 备份 → 分批执行 → 写后读取或后台抽样 → 异常回滚。

### 4. 数据存在不代表归属信息完整

残留接口账号分析中，现有数据能够识别 844 条，但大量账号的关联门店字段为空。因此“已识别的全部”不能直接等同于“业务上的绝对全量”。需要补充门店到账号的映射或确认官方数据口径后，才能决定清理和预警范围。

### 5. 富媒体与外部平台配置需要逐层检查

- 欢迎语：文件格式 → 素材上传 → `media_id` → appid/授权 → 消息发送；
- 小程序卡片：企业微信关联 → 飞冰功能开关 → path 参数 → 页面生成；
- 裂变群：业务错误码 → 底层平台错误码 → 第三方许可状态。

不同层级可能呈现相似的前端错误，不能只根据页面提示判断根因。

## 📌 今日总结（精华与可复用要点）

今天最重要的成果，是把“让 AI 帮忙完成某一次操作”推进为“让日常需求持续进入同一套能力生产机制”。分类、taxonomy、脚本、Skill、Git、dryRun、安全检查和留痕不再是孤立环节，而是连成了一条工作链。

可复用要点：

- **能力与客户数据分离**：脚本属于稳定能力，客户只是参数，避免同一逻辑复制多个品牌版本。
- **分类对齐真实系统边界**：按 Center 归位比按临时业务名称更稳定，也更容易从接口和源码定位责任域。
- **taxonomy 先于自动路由**：AI 若没有单一事实源，只能靠关键词猜测；有清单后才能稳定完成对象到能力的映射。
- **脚本、Skill、SOP 分层**：确定性执行交给脚本，判断与编排交给 Skill，无 API 的工作沉淀 SOP。
- **写操作默认保守**：默认 dryRun，显式开启 execute，要求备份确认，并支持分批、断点和执行报告。
- **共享不仅是 push**：代码进入 Git 之前必须完成脱敏、命名、元数据、测试和 taxonomy 登记；真实业务数据留在本机。
- **完成状态分级**：代码完成、预演通过、接口提交、业务展示验收与 PR 合并必须分别记录。

反思与改进：当前能力库完成了骨架、历史资产归位和首次真实验证，但仍有不少旧脚本缺少真正的 `.env` 接入或完整 dryRun；自动提交产生的 PR 仍需人工 review；业务留痕如何既满足团队复盘又避免客户数据进入远程仓库，也需要继续明确模板和边界。

最终价值：飞冰小组今后面对群链接、欢迎语、门店、账号、渠道码等需求时，可以沿统一规则定位和复用能力；新需求也能在处理后自动沉淀为脚本或 Skill，并通过 Git 与团队共享。今天的渠道欢迎语换图证明这条链已能服务真实业务，而不是停留在方案层。
