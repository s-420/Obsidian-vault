# Agent 处理业务会议准备

## 一、会议核心观点

飞冰业务 Agent 不应被理解为一个可以直接操作所有系统的聊天机器人，也不应一开始就建设通用 Agent 平台。更合适的目标是：

> 以 Agent 作为业务理解和任务调度入口，以 Skill 作为标准业务能力单元，以现有或重写后的业务系统作为确定性执行底座，再通过权限、审批、证据和验收形成可信闭环。

整体可以概括为：

> **一脑、多能力、强执行、重治理、闭环验收。**

- **一脑**：Agent 负责理解需求、澄清信息、规划任务和选择 Skill；
- **多能力**：把客服替换、群链接替换、欢迎语修改、账户激活等业务沉淀为独立 Skill；
- **强执行**：Java Service、API、任务队列、脚本和第三方接口负责确定性执行；
- **重治理**：身份、权限、审批、审计、成本、数据安全和止损贯穿全链路；
- **闭环验收**：必须通过真实业务数据证明结果，而不是只看接口返回或模型表述。

## 二、整体架构

```text
┌─────────────────────────────────────────────┐
│ 1. 人与业务入口层                            │
│ 客户 / 运营 / 产品 / 管理者                  │
│ 提出目标、补充现实信息、作出取舍和关键授权   │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 2. Agent 认知与调度层                        │
│ 身份识别 → 需求解析 → 信息澄清 → 风险判断   │
│ → 任务规划 → Skill 选择 → 执行过程协调       │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 3. Skill 业务能力层                          │
│ 客服替换 / 群链接替换 / 欢迎语修改 / 激活   │
│ 定义业务规则、输入输出、权限、工作流、       │
│ 验收标准、失败处理和版本                     │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 4. 确定性执行层                              │
│ Java Service / API / 数据库 / 消息队列       │
│ Node.js、Python 工具 / 第三方企微接口        │
│ 负责校验、幂等、事务、执行、重试和回滚       │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 5. 证据与验收层                              │
│ 日志 / 前后数据 / 任务状态 / 自动测试        │
│ 业务规则校验 / 独立评估 / 人工高风险确认     │
│ 不通过则重试、回滚、重新澄清或转人工         │
└──────────────────┴──────────────────────────┘

贯穿所有层：身份、权限、审批、审计、密钥、成本、
风险分级、数据脱敏、告警、回滚和止损。
```

### 1. 人与业务入口层：决定为什么做

人的职责是定义业务目标、补充现实信息、作出价值取舍、授予关键权限并承担最终责任。人不需要持续盯着 Agent，而应在业务方向、高风险操作和异常判断等节点介入。

### 2. Agent 层：理解目标并组织任务

Agent 负责识别用户意图、业务对象、影响范围、约束、缺失信息和风险，再选择合适的 Skill 并生成执行计划。

Agent 可以负责理解和规划，但不能自行扩大操作范围、绕过审批、关闭 dry-run 或执行超出用户权限的动作。

### 3. Skill 层：把业务能力标准化

Skill 不是简单包装 API，也不只是提示词或说明文档：

> **Skill = 接口能力 + 业务语义 + 使用规则 + 执行流程 + 验收标准。**

每个 Skill 至少需要明确业务目的、触发条件、禁止条件、输入输出、权限风险、业务不变量、执行步骤、成功证据、失败处理、负责人和版本。

### 4. 执行层：可靠完成真实操作

现有或重写后的后端系统负责参数校验、权限判断、幂等、事务、批量拆分、并发控制、异步任务、超时、重试、补偿和回滚。

> **模型负责理解和选择，Skill 负责表达业务规则，确定性代码负责校验和真实执行。**

### 5. 证据与验收层：证明业务真正完成

接口返回 200、脚本退出码为 0 或模型声称成功，都不能单独作为任务完成依据。系统需要组合：

1. **确定性验收**：参数、数量、ID 映射、任务状态、前后数据和测试断言；
2. **业务验收**：客服是否真实绑定、欢迎语是否实际生效、License 是否正确消耗；
3. **人工验收**：高风险批量操作、不可逆操作、客户内容触达和价值判断。

验收失败后应根据情况自动重试、回滚、重新澄清、停止告警或转人工。

## 三、Agent、Skill、工作流与 API 的关系

| 概念 | 主要职责 | 示例 |
|---|---|---|
| Agent | 理解目标、澄清需求、制定计划、选择能力 | 判断用户想批量更换客服 |
| Skill | 定义一个边界明确的业务能力 | 门店客服批量替换 |
| 工作流 | 规定多个步骤或 Skill 的执行顺序 | 查询→映射→预演→审批→执行→验证 |
| API / Service | 执行确定性的系统操作 | 修改某门店的客服绑定 |
| 验收器 | 根据证据判断业务是否完成 | 查询并对比实际绑定结果 |

> Agent 决定做什么，Skill 定义能做什么，工作流组织先后顺序，后端完成实际操作，验收层证明是否成功。

## 四、首个试点：门店客服批量替换 Skill

建议优先选择已有真实业务经验的“门店客服批量替换”，先跑通一个最小可信闭环：

```text
运营提交自然语言需求和 Excel
→ Agent 识别目标、范围、客服对象和风险
→ 缺少信息时向运营澄清
→ 选择“门店客服批量替换 Skill”
→ 校验三方 ID、门店 ID、手机号和企微 userID
→ 查询并保存变更前快照
→ 执行 dry-run，输出影响范围和异常清单
→ 人工确认正式执行
→ 创建异步任务并调用业务接口
→ 控制并发、幂等、超时和重试
→ 查询门店实际客服绑定情况
→ 对比变更前后数据
→ 输出成功、失败、跳过和待人工处理清单
→ 失败项重试、回滚或转人工
→ 执行记录进入异常案例和 Skill 迭代
```

第一版需要证明：

- 能发现缺失或异常输入；
- 能准确计算影响范围；
- 默认仅进行 dry-run；
- 未经授权不会正式写入；
- 重复执行不会产生重复副作用；
- 能查询并验证真实业务结果；
- 失败可以重试、回滚或转人工；
- 能生成完整、可审计的执行报告。

## 五、人的介入与渐进式授权

人的介入点包括：

- **业务开始前**：定义目标、业务价值和优先级；
- **执行前**：确认影响范围，审批高风险或不可逆操作；
- **执行中**：处理规则无法覆盖的异常和事实冲突；
- **执行后**：判断是否真正创造业务价值，并决定是否扩大自动化范围。

授权可以分阶段演进：

```text
第一阶段：AI 提计划，人执行
第二阶段：AI 提计划，人审批，系统执行
第三阶段：低风险自动执行，高风险人工审批
第四阶段：稳定流程自动运行，异常才转人工
```

## 六、会上可以直接表达的内容

> 我认为 Agent 处理业务的重点，不是先做一个通用平台，而是先选一个真实运营场景，把需求理解、Skill 调用、人工审批、系统执行和结果验证跑成完整闭环。
>
> 模型主要负责理解需求、补充信息和选择 Skill；权限、数据校验、审批、幂等、执行和回滚仍由后端系统负责。第一阶段可以采用“AI 计划—人工确认—系统执行—自动验证—异常转人工”的模式。
>
> 建议从门店客服批量替换开始，先证明它能够减少人工时间，同时保证结果可验证、过程可追踪、失败可恢复。稳定后再接入群链接、欢迎语和账户激活等能力，多个 Skill 出现共性需求后再抽取平台能力。

## 七、会上需要推动确认的问题

1. 当前最高频、最耗时且规则明确的运营任务是什么？
2. 第一个试点是否选择门店客服批量替换？
3. 涉及哪些现有接口、数据对象和人工操作？
4. 哪些操作可逆，哪些必须审批？
5. 如何查询并证明业务结果真正生效？
6. 谁负责提供脱敏测试数据和最终验收？
7. 第一阶段用成功率、耗时、人工接管率还是其他指标衡量？

## 八、风险与避免的误区

- 不要把 Agent 等同于聊天入口，忽略后端执行和治理底座；
- 不要把 API 调用成功等同于业务结果成功；
- 不要先设计通用平台，再寻找业务场景；
- 不要让同一个模型在相同上下文中完成执行和自我验收；
- 文档、代码、客户表述和实时数据冲突时，应标记冲突并向责任人确认；
- 权限、范围、金额、审批和验收指标必须使用精确、可执行的定义。

## 九、会议希望得到的结果

本次会议不需要一次确定完整平台架构，最重要的是形成以下明确结果：

- 确定首个试点业务；
- 明确业务负责人和技术负责人；
- 明确输入数据和现有接口；
- 明确风险等级、审批边界和回滚要求；
- 明确什么证据代表业务真正完成；
- 明确第一阶段的时间范围和衡量指标。

最终希望实现的是：运营人员只需要表达业务目标，Agent 负责理解和组织，Skill 与后端负责安全执行，系统最终交付可验证、可追踪、必要时可回滚的真实业务结果。
