## 🐛 踩坑与排查

### 1. 前端“能运行”不等于“设计完成”

- **表现**：仅检查代码和构建结果，无法发现信息层级、视觉一致性、交互状态、窄屏溢出及真实使用体验问题。
- **解决思路**：把前端工作升级为“读取项目视觉上下文 → 建立设计契约 → 分层实现 → 浏览器逐页检查 → 根据缺陷迭代”的闭环。
- **验收点**：DailyFlow 小窗与 5 个管理页面完成可见回归；关键交互、820px 响应式和浏览器控制台均已检查。

### 2. Electron 退出阶段存在窗口生命周期竞态

- **现象**：应用退出并保存窗口位置时，可能访问已经销毁的 `BrowserWindow`，导致主进程 JavaScript 错误窗口。
- **解决思路**：在窗口销毁后禁止继续读取状态，并取消释放后的延时保存任务；补充边界回归测试。
- **验收点**：修复版通过真实启动与系统关闭测试，进程正常结束，未再次出现错误窗口或残留进程。

### 3. DailyFlow 缺少 Git 证据链

- **表现**：当前项目目录不是 Git 仓库，虽然已有代码、测试、安装包和验收报告，但缺少分支、提交与版本变更记录。
- **影响**：不利于回溯个人修改、证明项目演进过程，也会削弱后续简历与面试中的工程证据。
- **改进**：经用户确认后初始化 Git，补齐 `.gitignore`、阶段提交、版本标签及后续 Issue/提交规范。
- **二次确认**：初始化仓库、创建远程仓库或发布代码前，确认代码归属、敏感信息和可公开范围。

### 4. 方法论需要真实项目验证

- **不足**：AI 原生 Skill 架构和前端设计 skill 的思路已经形成，但长期价值取决于能否稳定复用于不同项目，而不是只在一次任务中有效。
- **改进**：继续选择真实项目进行复用，记录输入条件、执行过程、缺陷、验收证据和需要调整的规则。

### 5. 项目完成后才补 Git，证据链建立过晚

- **现象**：DailyFlow 已完成需求、开发、测试和 Windows 构建，但项目尚未初始化 Git，无法从版本历史还原各阶段为什么修改、修改了什么以及如何验收。
- **根因**：原有 `project-workspace`、`vibecoding-sop` 和 `brownfield-iteration` 只关注目录、开发与测试，没有把 Git 基线和阶段提交作为流程门禁。
- **解决思路**：把 Git 规则前移到项目创建和每次存量迭代：开发前检查现场，每阶段汇报差异和验证证据，经用户确认后提交；远程仓库和推送继续单独授权。
- **当前结果**：相关日报、周报和项目开发 Skill 已完成升级，全局候选规则已进入 inbox；DailyFlow 完成只读预检，初始化与首次提交延期至明天。

- **知识资产**：今天形成 AI 原生架构文档、系统设计图、职业发展规划、求职推进方案、前端设计 skill 和实习周报，多项成果已通过链接纳入知识库结构。

- **可复用方法——能力建设闭环**：
  1. 从真实需求或个人短板中确定能力目标；
  2. 将处理方法封装为带触发条件、流程和验收标准的 skill；
  3. 选择真实项目试用，而不是只验证文档完整性；
  4. 通过测试、构建、视觉检查和发布产物收集证据；
  5. 根据实测缺陷反向修订 skill 和项目规范。
- **反思与改进**：今天的文档和 AI 协作产出较多，下一阶段应减少继续扩展概念，优先补齐 DailyFlow 的 Git 证据链、最终用户验收，以及飞冰真实业务 Skill 的端到端执行证据。
- **最终价值**：后续 Agent 开发项目时会从一开始重视 Git、测试和验收证据；日报可以回收当天成果，周报可以聚合一周主线，最终为复盘、交接、求职简历和项目面试提供可追溯的真实资产。
