## 🐛 踩坑与排查

1. **dryRun 跑通 ≠ 流程正确。**今天 6 次 dryRun 先后暴露姓名匹配、模板店入参、群匹配过严等问题。只有把每一步的"预期状态"写成可断言的结果，dryRun 才有意义。
2. **写接口的"默认值"会静默篡改业务。**渠道更新接口在缺少 `tagSwitch` 时默认打标签——界面上看不出来，只有回读全字段对比才发现。可复用做法：**提交前快照 → 提交后回读 → 全字段 diff → 不一致立即回滚**，并把它固化进脚本而不是靠人工记住。
3. **字符串拼接的空值会污染线上数据。**`name=nullnull` 导致门店更新被拒。修复之外更重要的是**补上续作能力**：已创建的门店要能接着跑完后续步骤，而不是重跑导致重复建店、重复消耗激活码。
4. **接口字段命名与业务叫法不一致。**"桌台码"在接口里有 `GROUP`/`CHANNEL`/`SINGLE` 等多种类型，按名称或类型猜都会漏。涉及交付清单时，以"同一模板拷贝出的实体 + 逐个校验负责人"为准。
5. **同一图片可能有多个域名。**`fbhsay.su.bcebos.com` 与 `boshsay.feibing.tech` 指向同一资源，比对前必须规范化域名，否则会误判为"未更新"。
6. **外部披露要有边界。**安全审查（guardian）拦截了一次把门店完整地址发给高德地图的请求，理由是用户只授权了飞冰企业内的操作，未授权向第三方披露该地址。**同一类数据在内网可用、外发需另行授权**，这条边界今天被自动拦了一次，值得保留。

## 📌 今日总结（精华与可复用要点）

今天最重要的成果，是把"新建门店"这类原本靠人肉点后台、一步错就要重来的工作，推进成**可预演、可续作、可回滚、可交付**的脚本流程，并且用一次真实线上试跑验证了 11 步链路和最终交付物（11 个桌台码 + 全渠道负责人校验通过）。

可复用要点：

- **SOP 先于代码**：今天真正耗时的是和用户对齐"顺序、谁负责、失败怎么办"，代码只是把共识固化下来。顺序错了，脚本跑得越快错得越多。
- **高风险写操作四件套**：默认 dryRun → 显式 `--execute` → 提交前重新校验 → 提交后回读 diff + 可回滚。
- **续作比重试安全**：涉及消耗品（激活码）和不可重复动作（建店）的流程，必须支持从中间步骤继续。
- **失败要"停得住"**：群主不一致、配置发生变化的场景，选择停止而不是降级执行，避免把错误绑定写进线上。
- **数据核查先行**：13,351 条换图需求，先摸清重复门店、卡片变体、异常记录再动手，才能给出"13,275 可改 / 75 待核实"这种可交付的结论，而不是一句"批量改一下"。

最终价值：建店需求以后可以从"接单—点后台—发码"压缩为"填一份 JSON—预演—执行—交付"，且线上风险可控；渠道换图类需求则形成"核查 → 备份 → 小批量试跑 → 回读验证 → 扩大执行"的固定套路。今天尚未完成的是把原始工单正式落地和把 13,275 条批量提交，这两项都卡在"验证未完成"，不写成已交付。
