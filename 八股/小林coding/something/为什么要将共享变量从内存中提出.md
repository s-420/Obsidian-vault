用最纯粹、最直接的硬件大白话来回答，是因为：为了实现锁的“可见性”，如果不强行剔除缓存，线程就会因为“盲目自信”而永远在看旧报纸，从而导致严重的“脏读”和数据冲突。

我们用两张最直观的硬件对比图景，来看看“剔除”这个动作到底在拯救什么：

## 1. 致命隐患：如果没有“加锁强行剔除”的机制

由于 CPU 核心（线程）的速度比大内存条快 200 倍，它只要读过一次变量（比如 `tickets = 10`），就会把这个值死死缓存在自己的大脑（工作内存/L1/L2缓存）里。

- 灾难发生：此时，另一个线程把主内存里的票数改成了 `9`。
- 盲目自信：当你的线程获取锁成功、高高兴兴冲进房间准备继续卖票时，如果 JVM 不去强行清理它的大脑，它就会盲目相信自己缓存里的那个旧数字 `10`，它根本不知道外面的世界已经变了！它拿着旧的 `10` 继续去扣减，并发问题就此爆发。

## 2. 强行剔除：JVM 下达的“洗脑”死命令

为了彻底杜绝上面的悲剧，Java 内存模型（JMM）规定，当线程获取锁成功（进入 synchronized 块）的瞬间，JVM 必须对这个线程的 CPU 核心下达一条沉重的硬件指令（内存屏障）：

- 洗脑抹除：把你脑子（工作内存）里缓存的所有关于这个共享变量的信息，全部连根拔起、彻底抹黑、强行剔除！
- 被迫看世界：由于自己的缓存被剔除干净、变成了一片空白，这个线程就无法再盲目自信了。它在接下来的运行中，必须卑微地迈开腿、走远路，亲自去大内存条（主内存）里，把别人刚刚改好的最新的 `9` 重新拉取一份到脑子里。

---

## 🎯 终极闭环：剔除的底层本质

获取锁时的“将共享变量剔除出工作内存”，在底层硬件上就是将 CPU 缓存行（Cache Line）强制置为“失效状态（Invalid）”。

它存在的唯一目的，就是强行打破 CPU 核心的自私与傲慢，逼着它在拿到锁准备大干一场的瞬间，必须先“刷新刷新缓存”，去向主内存看齐。只有这样，锁的“互斥排队”才有意义，因为后面进来的人才能永远拿到最新、最正确的数据。
