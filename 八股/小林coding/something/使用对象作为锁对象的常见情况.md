将对象本身作为锁对象（即 `synchronized(obj)`），是大厂高并发开发中最经典、最高频的操作。

这种做法的核心思想是：“谁的肚子里装了数据，就用谁的身体当大门来加锁”。只有这样，才能让锁和它所保护的业务数据完美实现“形影不离”。

在实际开发中，主要有以下 4 种最经典的适用情况：

## 1. 桶的头节点锁（如 `ConcurrentHashMap`）

这就是我们前文死磕过的终极方案。当一个超大容器被切分成很多个独立的区域（桶）时，我们不需要一把全局的大锁，而是需要很多把针对具体区域的小锁。

- 情况描述：数组的每个格子就是一个桶，桶里躺着的第一个元素就是“头节点”对象。
- 为什么用它当锁：因为你想修改 5 号桶的数据，而 5 号桶的唯一入口就是这个头节点。所以直接执行 `synchronized(头节点对象)`，直接用这个首个元素当大门，完美实现了只锁 5 号桶、不影响其他桶的极致并发 [I4]。

## 2. 核心业务资源锁（如“账户对象”或“货架对象”）

在设计面向对象的电商或银行系统时，我们会把数据和方法封装在具体的业务对象里。当你想保护这个对象内部的数据不被改毁时，直接用它自己当锁是最天然的。

- 情况描述：银行转账系统。
- 为什么用它当锁：
    
    ```java
    public class Account {
        private int balance; // 银行余额
    
        public void transfer(int amount) {
            // 直接用当前账户对象（this）作为锁！
            synchronized(this) { 
                this.balance -= amount;
            }
        }
    }
    ```
    
    每个人都持有自己独立的 `Account` 实例对象。当 A 去取钱时，只锁住 A 的 `this` 对象，此时 B 去取钱，锁住的是 B 的 `this` 对象。对象状态（余额）与锁（对象本身）紧密相关，既安全又实现了不同账户之间的完全并发。

## 3. 多个线程协作的“信号灯”对象（线程通信）

当你需要两个线程通过 `wait()` 和 `notify()` 互相配合、一唱一和地干活时（例如经典的生产者与消费者模式），必须用一个共享的对象来充当它们的“联络站”。

- 情况描述：线程 A 负责生产蛋糕，线程 B 负责吃蛋糕。它们共享一个 `List` 集合或者一个空的 `Object lock = new Object();`。
- 为什么用它当锁：因为 Java 规定，`wait()` 和 `notify()` 必须在持有了该对象的锁之后才能调用。
    
    ```java
    synchronized(lock) {
        while (队列满了) {
            lock.wait(); // 蛋糕师在 lock 对象上睡着，并释放 lock 锁
        }
        // 生产蛋糕...
        lock.notify(); // 唤醒在 lock 对象上睡觉的吃货
    }
    ```
    
    在这里，这个特定的对象充当了两个线程公用的“传话筒”和“歇脚处”。

## 4. 局部细粒度化锁（临时创建的 Dummy 对象）

有时候，你的类是一个非常庞大的单例 Service（比如 `OrderService`），里面有几百行代码。你只想保护其中某 3 行敏感的改动（比如修改一个全局计数器），如果直接锁整个方法（锁 `this`），会把整个类都卡死。

- 情况描述：大方法里面的局部敏感代码块。
- 为什么用它当锁：程序员会在类里面偷偷定义一个没有任何业务意义的、纯粹用来当看门大爷的工具对象：
    
    ```java
    private final Object counterLock = new Object(); // 纯粹为了加锁而生的对象
    
    public void doSomething() {
        // 前面 100 行不加锁，大家并发跑...
    
        synchronized(counterLock) { // 只用这个专属对象锁住核心的 3 行
            globalCounter++;
        }
    
        // 后面 100 行也不加锁...
    }
    ```
    
    这种情况就是为了把锁的范围（粒度）缩到最小，用一个独立的工具对象来保护一笔特定的资产。

## 🎯 终极闭环：为什么能用“任意对象”当锁？

你可能会问，为什么 Java 允许随便 new 一个 `Object` 或者拿任何业务对象就能直接当锁使？

- 底层真相：因为在 JVM 的设计中，任何一个 Java 对象在出生时，它的头顶上（Mark Word 区域）都天然自带了一把隐藏的锁（Monitor 监视器）和一根隐形的绳子（等待队列）。
- Java 之父为了让面向对象的逻辑更纯粹，才允许你顺手牵羊，直接拿跟业务数据紧密相连的那个对象本身来当锁大门，这就是“内置锁”的由来。
